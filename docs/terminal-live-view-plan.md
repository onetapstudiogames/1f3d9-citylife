# Terminal live view: plan (2026-09-07)

Owner corrections for implementation: animate a walk only from a new recorded
public move event, never from a difference between presence snapshots. Positions
inside each room are decorative; disclose that in the skill text, never on screen.
These corrections govern the original motion description and step 10 below.

Owner wants: cozy, cute, visuals first, like the Sims; residents, things and places drawn from their own 8x8 portraits; almost no words.

## recommendation

Rebuild the live view as a small drawn window that paints pictures and almost nothing else: soft room boxes whose floor is made from the place's own drawing, resident faces and thing marks drawn from their own 8x8 pixels, a gentle drift, a walk when the record says someone moved, and a short speech bubble when there is a note. Keep the plumbing that already works (the anonymous public reads in city.mjs, the half-block portrait trick, the wt.exe / cmd-start window opener) and replace the screen layer above it. Everything wordy comes off: counts, "+N more", the event ticker, the legend, the refresh notice, the handles under the faces. The only words left are the place name and the room names, plus one bottom line that stays blank unless a read fails. Build it in 15 small steps, each shippable on its own and each reviewable by replaying a recorded scene from a file instead of the live city.

## needs_library

No library. Plain Node plus ANSI does this well, and the current code already proves the two hard parts: half-block pixel portraits and opening a real terminal window on all three platforms. What the rebuild adds - a back buffer, a cell-by-cell diff so only changed cells get written, the alternate screen, a hidden cursor, synchronized output, raw-mode keys, and resize handling - is a couple of hundred lines of built-in Node (process.stdout, readline.emitKeypressEvents, process.stdin.setRawMode, process.stdout.on('resize')). The candidates were weighed and none earn their place: ink needs Node 22 and drags in React, a WASM flexbox engine and about fifteen packages to lay out boxes we are already laying out by hand; blessed has not shipped since October 2024 and wants to own the event loop; terminal-kit is the only one still actively maintained (July 2026) but buys nothing we would not write anyway, and adding it would end the plugin's zero-dependency install, which is what lets an agent install this skill with no build step.

## portraits

All three kinds of drawing go through one routine. A drawing is 8x8 pixels: a palette of hex colours and 64 slots each holding a palette index or nothing. One text cell can hold two stacked pixels by printing the upper-half-block character with the top pixel as its colour and the bottom pixel as its background, so an 8x8 drawing becomes 8 characters wide and 4 lines tall. Only the top pixel painted, print the upper half block; only the bottom, the lower half block; neither, a space so the floor shows through. That is exactly what the plugin does today, so the code carries over. Residents keep full size, 8 wide by 4 tall, about a thumbnail. Things get a half-size mark: shrink the 8x8 to 4x4 by taking each 2x2 group of pixels and keeping the colour that appears most in it (ties go to the top-left, a group with no paint stays empty), then run the same half-block trick for a mark 4 wide by 2 tall. Reason: a thing at full size fights the residents for the eye and eats floor a room does not have, while at 4x2 it keeps its own colours and reads as an object sitting on the ground. A resident with no drawing keeps the grey four-line figure the plugin already draws. A thing with no drawing gets a 4x2 grey silhouette in the muted colour - clearly a thing, clearly not drawn, and never a word about it. Colour goes out as 24-bit truecolor when the terminal says it can take it (COLORTERM says truecolor or 24bit, or WT_SESSION is set, or iTerm2); otherwise every hex snaps to the nearest of the 256 xterm colours, and if even that is refused, to the nearest of the basic 16, where the shapes still read though the palette flattens. One small function does that snapping, so there is a single place to fix it.

## floors_and_things

Both, and the split is deliberate. A place's 8x8 drawing becomes the room's ground by tiling: one tile is 8 characters wide and 4 lines tall, repeated across the whole inside of the box, so the first town's dark-green-with-scattered-lighter-flecks reads as actual grass rather than a stamp in a corner. Every tiled pixel is blended about halfway toward the room's base dark before printing, so the floor stays quiet and the residents stay the brightest thing on screen; pixels the drawing left empty print nothing, which is what gives the first town's few gaps their bare patches. The same drawing also sets the walls: take its two most-used colours, lighten the brighter one, and use it for the box border and the room name, so a room looks like itself before you read anything. A place with no drawing gets a plain soft floor in the theme's room colour and a muted border - calm, not broken, and nothing on screen mentions it. Things sit on that floor as their 4x2 marks (or the grey silhouette when undrawn) and are placed first, at spots worked out from the thing's id so they never jump between frames. Residents and things never cover each other because the room keeps a simple map of taken ground: anything placed claims its own cells plus a one-cell margin, and a resident only takes a spot, or a drift step, onto cells that are free. A room shows at most five thing marks; every thing past the fifth becomes one small dot in a quiet row along the bottom edge, up to a dozen dots, and past that the row simply stops. The dots are the count - there is no number. Because the place read does not say which things are drawn, each shown thing needs its own drawing fetch, so only those first five are ever fetched, the answer is remembered for the life of the window, and "not drawn" is remembered too so a thing is never asked about twice.

## motion

Two clocks, kept apart. The record is read every 30 seconds, unchanged from today. The screen paints up to 8 times a second, and only when something actually changed - a drift step, a walk in progress, a bubble appearing or expiring, a fresh read, a resize. When the city is still, the loop paints nothing and costs nothing. No flicker, by three tricks: draw into the alternate screen so the shell's scrollback is untouched and comes back exactly as it was; hide the cursor for the whole session; and build each frame in memory, compare it cell by cell with what is on screen, and write only the runs that differ, wrapped in the synchronized-output escape (CSI ?2026h before, CSI ?2026l after) so terminals that understand it paint the frame in one go and terminals that do not just ignore two harmless sequences. Never clear the screen between frames - the current clear-and-redraw is the flicker. Drift: each resident gets a home spot on arrival, and every two to four seconds one resident steps to a free neighbouring cell, only if it stays within a couple of cells of home. A few move at a time, so the room breathes rather than churns. Walks: after each read, compare where every resident was with where they are now. Same room, nothing happens. Different room with both rooms on screen: the layout keeps a one-cell lane between boxes and a door gap in each facing wall, and the resident walks out of their door, along the lane, in through the other door, then settles into a free spot - about two seconds, one step every few frames. If the other room is off screen they walk to their door and fade out over two frames, and an arrival from off screen does the same in reverse. Bubbles: a note that was not in the previous read gives its author a small rounded bubble just above their head for six seconds, holding the first couple of dozen characters and no author line, because the face underneath already says who. One bubble at a time per room, a second note waits its turn, and nobody who is off screen gets one. Nothing else moves - no spinner, no ticking clock, no counters.

## keys

Four things, none of them printed on screen. q, Esc, or Ctrl+C closes the window - the alternate screen goes back, the cursor comes back, one plain line says it closed. r reads the record now instead of waiting out the 30 seconds. Left and right arrow move to the town before or after this one in the same continent, using names the directory read already gives. That is all. Raw-mode keys are only switched on when stdin is a real terminal; if it is not, the view still runs and Ctrl+C still ends it. What stays off the screen: resident counts, thing counts, "+N more", the recent-events ticker, the legend explaining what a portrait means, the "refreshed every 30 seconds" notice, the breadcrumb of parent places, the clock, handles under the faces, and any list of anything. On screen there is the place name small in the top-left, the room boxes with their floors and names, the faces, the thing marks, the dots, the occasional bubble, and one bottom line that is blank almost always. The key list, and the fact that positions inside a room are made up for looks, live in the skill's own text, not in the window.

## windows

Windows Terminal is the good case: it turns escape handling on by default, does 24-bit colour, handles UTF-8 without help, understands synchronized output in 1.25 and later, and reports resizes properly. Launch it the way the plugin already does, with wt.exe new-tab. The old console is the fallback the plugin drops to when wt.exe is missing - cmd's start opening PowerShell with -NoExit - and it differs in four ways that matter. It does not have escape handling on by default, so the script must ask for it and must not assume it worked. Its default code page is not UTF-8, so half blocks and box-drawing characters come out as garbage unless the code page is switched to UTF-8 as the first thing in the launched command line, before Node starts. It probably does 256 colours but truecolor is only there on newer builds, so treat it as 256 unless COLORTERM says otherwise. And synchronized output has never been confirmed there, so skip it and lean on the diff writer, which keeps ordinary frames tiny anyway. Detection is simple: on Windows, WT_SESSION present means Windows Terminal, absent means treat it as the old console. Its default window is 80 by 24, which fits about two rooms with floors and things, so the layout must be computed from the real window size every paint and drop rooms rather than squeeze them. If after all that the escapes are clearly not being handled - the first frame writes literal escape characters instead of colour - the script stops trying to animate, prints one quiet line saying this console cannot show the drawn view, and falls back to the single plain-text frame the plugin already has. That fallback exists today and stays; it is the honest floor.

## steps

1. 1. Record a scene to a file. A small script does one pass of the public reads for a chosen place - directory, outline, the place's rooms, notes, events - plus every drawing it needed (place drawings, resident drawings, thing drawings), and writes them into one JSON file. Then extend that file by hand into three moments: a starting one, one where a resident has changed room, one where a new note exists. This is the fixture every later step gets reviewed against.
2. 2. Let the view read from the file instead of the city. One switch, --scene <file>, feeds the same shapes into the same code. Ship this before touching any drawing, so from here on every step can be shown by replaying the same scene and nothing needs the live city to review.
3. 3. Rebuild the screen underneath. Alternate screen on, cursor hidden, clean exit on q, Esc, Ctrl+C and on any crash; frames built in memory and written as a cell-by-cell difference; synchronized output around each write; layout worked out from the real window size and redone on resize. Content stays exactly what it is today. Review: replay the scene, resize the window, press q, confirm the shell looks untouched and nothing flickers.
4. 4. One place that turns a colour into an escape. Truecolor when the terminal says so, nearest of 256 otherwise, nearest of 16 as the floor, decided once at startup. Review: replay the scene with the truecolor hint on and off and compare.
5. 5. Take the words off. Delete the counts, the '+N more', the event ticker, the legend, the refresh notice, the handles under the faces. Rooms become soft rounded boxes sized to the window. Review: the replayed scene shows boxes, room names and faces - nothing else.
6. 6. Floors from place drawings. Fetch each shown room's place drawing once and remember it; tile it dimmed across the floor; tint the border and room name with its brighter main colour. A room with no drawing gets a plain soft floor and a muted border. Review: the scene has the drawn first town and an undrawn room side by side.
7. 7. Residents on the floor. Faces at full size, placed on free ground, with the room keeping a map of which cells are taken. Grey figure when a resident has no drawing. Review: a crowded room in the scene with nothing overlapping anything.
8. 8. Things on the floor. One drawing fetch per shown thing, remembered for the life of the window including the 'not drawn' answer. Drawn thing becomes a 4x2 mark from its shrunk 8x8; undrawn thing becomes a grey 4x2 silhouette; at most five marks per room and the rest become a quiet row of dots. Review: the scene has one drawn thing, one undrawn thing, and a room holding more than five.
9. 9. Drift. Stable home spots per resident, one step every few seconds inside a small radius, never onto taken ground, only a few residents moving at once; paint only when something changed, up to 8 times a second. Review: replay for half a minute and watch that nothing overlaps, nothing flickers, and a still resident stays still.
10. 10. Walks. Compare each read with the one before it; a changed room means a walk out of one door, along the lane between boxes, in through the other, then settling. Off screen at either end means walking to the door and fading. Review: the scene's second moment moves one resident between two rooms.
11. 11. Bubbles. A note that was not there before puts a short bubble over its author for six seconds, one at a time per room, queued if two land together, none for someone off screen. Review: the scene's third moment adds a note.
12. 12. The quiet line. One blank line reserved at the bottom. When a read fails, keep the frame exactly as it is and write one short line there in the muted colour; clear it the moment a read succeeds. No stack traces, no retry counters, no blank screen. Review: tell the replay to fail a read.
13. 13. Keys. q, Esc and Ctrl+C close; r reads now; left and right move between towns. Raw mode only when stdin is a real terminal. Nothing about keys appears on screen. Review: replay the scene and press each key.
14. 14. The old Windows console. Treat a missing WT_SESSION on Windows as the old console: switch the window to UTF-8 before Node starts, assume 256 colours unless told otherwise, skip synchronized output, and fit 80 by 24 by showing fewer rooms rather than squeezing them. If the escapes are clearly not being handled, print one quiet line and drop to the single plain-text frame the plugin already has. Review: run it in Windows Terminal and in a cmd-started PowerShell window and screenshot both.
15. 15. Tests and the skill text. Unit tests for the floor tiling, the 8x8-to-4x2 shrink, the never-overlap rule, the walk path, the bubble timing out, and the colour snapping, plus one text snapshot of a replayed frame. Then update the skill's page: what you are looking at, the four keys, that positions inside a room are made up for looks, and that every read is public and anonymous.

## risks

- Fetching a drawing for every shown thing multiplies requests. Five per room across nine rooms, plus room drawings and faces, is roughly forty requests on the first paint of a busy town. Nobody has checked what the city does to an anonymous reader at that rate; if it starts refusing, the view goes quiet and only the honest line shows.
- Half blocks and box-drawing characters depend on the font and the code page, not on the terminal alone. The old Windows console with a default font and code page shows them as garbage, and there is no reliable way to detect that from inside the script - forcing UTF-8 helps, it does not guarantee.
- Synchronized output is confirmed on Windows Terminal, tmux and Ghostty but not on the old Windows console or Apple's Terminal. Without it, a full repaint (a resize, changing town) can tear. Ordinary frames are tiny because of the diff writer, so the exposure is limited to those moments.
- Snapping truecolor down to 256 flattens faces that use close shades - a seven-colour face may come out looking like five. Still cozy, no longer the artist's exact colours.
- Painting several times a second keeps a process busy for as long as the window is open. This machine already starves tools under load. Painting only when something changed is the main defence, but on a loaded machine walks and drift will still come out uneven.
- Positions inside a room are invented, and there is no room on screen for a sentence saying so. Someone will read a face standing next to a thing as a fact about the city. The only defences are that a resident is never drawn in a room the record does not put them in, and that the skill's text says it plainly.
- Walks are inferred from two snapshots 30 seconds apart. A resident who moves twice in that gap is drawn taking one walk. Honest about the endpoints, lossy about the middle, and it must never be dressed up as more.
- A small window cannot hold nine rooms with floors and things. The layout drops rooms rather than squeezing them, and drops them without saying so, because nothing is allowed to nag. That is a deliberate trade and it does hide part of the place.
- Replaying a fixture proves the drawing, not the city. If the public read shapes change, every replay still passes and the live view breaks. The scene recorder is the mitigation - fixtures get re-recorded, never hand-patched - plus one manual live check before shipping.
- There are no tests over the current render code at all, and this rebuild changes enough of it that 'port what works' really only covers the half-block routine and the window opener. The rest is new code needing new tests, and step 15 is where that debt gets paid, not earlier.
